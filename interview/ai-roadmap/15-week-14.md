The tool-calling loop you build on Day 97, in outline:

```python
messages = [{"role": "user", "content": "Do I need an umbrella in Mumbai today?"}]
while True:
    resp = client.messages.create(model="claude-sonnet-5-5", max_tokens=500,
                                  tools=tools, messages=messages)
    messages.append({"role": "assistant", "content": resp.content})
    if resp.stop_reason != "tool_use":          # the model gave a final answer
        break
    results = []
    for block in resp.content:
        if block.type == "tool_use":            # the model asked us to run a tool
            output = run_tool(block.name, block.input)
            results.append({"type": "tool_result", "tool_use_id": block.id, "content": output})
    messages.append({"role": "user", "content": results})   # send results back
print(resp.content[0].text)
```

## What each topic means

**Grounded answer.** An answer based only on the provided documents, not on the model's general memory. The prompt should demand it and say what to do when the answer is missing.

**Out-of-scope question.** A question the documents cannot answer. A good RAG app says "I could not find this in your documents" instead of guessing.

**FastAPI.** A modern Python web framework for building APIs. You write normal functions with type hints, and FastAPI handles HTTP, validation and automatic docs at `/docs`. You learn it deeply in Phase 7.

**Endpoint.** One URL + method your API offers, like `POST /ask`.

**Pydantic model.** A Python class that defines the shape of data (fields and types). FastAPI uses it to check that requests are valid: `class AskRequest(BaseModel): question: str`.

**Ingestion.** The pipeline that takes a new document and makes it searchable: extract text, chunk, embed, store.

**Evaluation set (golden dataset).** A fixed list of test questions with expected answers (and here, expected pages). You run the app on it after every change to see if it got better or worse.

**Hit rate@k (recall@k).** The share of test questions where the correct chunk is in the top k retrieved results. If the right page is in the top 5 for 16 of 20 questions, hit rate@5 = 16/20 = 0.8.

**Answer correctness and faithfulness.** **Correctness**: does the answer match the expected answer? **Faithfulness**: is every claim in the answer supported by the retrieved context? An answer can be correct but unfaithful (the model knew it from training), which is risky.

**Before/after table.** A small table showing a metric before and after one change. It is the best evidence for your README and interviews: "reranking raised answer correctness from 70% to 82%".

**Architecture diagram.** A simple picture of the parts of your system and how data flows between them. Every serious project README should have one.

**Demo video.** A 1–3 minute screen recording showing the app working, with your voice explaining it. Recruiters watch videos more often than they run code.

**Resume bullet.** One line describing what you built, how, and the result with a number. Example: "Built a RAG chatbot over 200-page PDFs (FastAPI, Chroma, Claude); hybrid search raised retrieval hit rate from 70% to 85% on a 30-question eval set."

**Project pitch.** A 2-minute spoken explanation: the problem, your solution, the architecture, one hard challenge and how you solved it, the result, and what you would improve.

**Tool calling (function calling).** You describe functions to the model (name, description, parameters as JSON Schema). Instead of answering, the model can reply "please call `get_weather` with `{"city": "Mumbai"}`". Your code runs the function and sends the result back; then the model answers using it. The model never runs code itself.

**JSON Schema.** A standard way to describe the shape of JSON data: which fields exist, their types, and which are required. Tools use it to define their parameters.

**`tool_use` and `tool_result`.** In the Anthropic API, a `tool_use` block is the model's request to call a tool (with an ID and inputs). You reply with a `tool_result` block that carries the same ID and the output. OpenAI's API has the same idea with different names (`tool_calls` and role `tool`).

**Stop reason.** Why the model stopped generating. `"tool_use"` means it is waiting for a tool result; `"end_turn"` means it has finished its answer; `"max_tokens"` means it hit the length limit.

**Parallel tool calls.** The model can ask for several tools in one turn (weather in Delhi and in Mumbai). Run them, ideally at the same time, and return all results together.

**Tool errors.** When a tool fails, send the error message back as the tool result (often with an error flag) so the model can retry or explain, instead of crashing your app.

**Agent (preview).** An LLM that runs in a loop, choosing tools step by step until a goal is reached. You study it fully next week.

**DP on sequences (DSA).** Problems like Longest Increasing Subsequence and Word Break, where dp[i] stores the best answer for the first i items and is built from earlier dp values.

**0/1 knapsack pattern (DSA).** Choose items, each used at most once, to reach a target. Partition Equal Subset Sum and Target Sum are this pattern.

## End-of-week self-check

1. How does your RAG app decide to say "I don't know"?
2. What is the difference between retrieval hit rate and answer correctness? Why measure both?
3. Your answers are wrong but the right chunk is retrieved. Where is the problem, and what would you try?
4. The right chunk is not retrieved. What would you try?
5. In tool calling, who actually runs the function?
6. What does `stop_reason == "tool_use"` mean, and what must your code do next?
7. Why should a tool's description be written carefully?
8. What is the recurrence for Coin Change (minimum coins)?

**Answers**

1. The prompt tells the model to answer only from the provided context and to say "I don't know" if the answer is not there. You can also add a similarity threshold: if no chunk scores above it, skip the LLM call and reply directly.
2. Hit rate checks whether the search found the right chunk; correctness checks whether the final answer is right. Measuring both tells you which half of the system to fix.
3. In generation. Try a clearer prompt (answer only from context, quote the relevant line), put the most relevant chunk first, reduce noisy extra chunks, or use a stronger model.
4. Try better chunking (size, overlap, keep headings), hybrid search with BM25, a reranker, query rewriting, a better embedding model, or metadata filters.
5. Your code. The model only outputs the tool name and arguments; your program runs the function and returns the result.
6. The model is asking for one or more tools to be run. Your code must run each requested tool, then send the results back as `tool_result` blocks with the matching IDs, and call the model again.
7. The model chooses tools and fills their arguments based only on the name, description and schema. A vague description leads to wrong tool choices or bad arguments.
8. dp[0] = 0; dp[a] = min over coins c ≤ a of dp[a − c] + 1; amounts that cannot be made stay at infinity, and the answer is dp[amount] (or −1 if infinite).
