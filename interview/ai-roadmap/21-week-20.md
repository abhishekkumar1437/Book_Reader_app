## What each topic means

**Sign-up and login.** Sign-up creates a user record; login checks the password and gives the client a token for later requests.

**Password hashing.** Never store passwords as plain text. Store a slow, salted hash (with a library such as `bcrypt` or `argon2`), and compare hashes at login. If the database leaks, the passwords stay protected.

**Access token.** A signed token (often a JWT) that proves who the user is on each request. Give it an expiry time.

**Multi-tenancy.** One app serving many users (tenants) whose data must stay separate. In RAG, every chunk carries a `user_id` and every search filters by it. Forgetting the filter is a serious data leak.

**Front end and back end.** The **front end** is what the user sees and clicks (the UI). The **back end** is the server code and data (your FastAPI app, databases).

**Health-check endpoint.** A simple route like `GET /health` that returns OK when the app and its dependencies are working. Cloud platforms use it to restart broken containers.

**`.env.example`.** A file in the repo listing every required environment variable with fake values, so others know what to set. The real `.env` stays out of Git.

**Persistent storage.** Disks or managed databases that keep data when containers restart or are replaced. Containers themselves should be treated as disposable.

**HTTPS.** Encrypted HTTP. Required for login pages; most container platforms provide it automatically.

**Structured logging.** Logging in a consistent machine-readable format (usually JSON) with fields like `request_id`, `user_id`, `latency_ms`, `input_tokens`, so logs can be searched and turned into charts.

**Request ID.** A unique ID attached to every log line of one request, so you can follow it through the whole system.

**Cost per request.** Input tokens × input price + output tokens × output price (+ embedding and infrastructure costs). Tracking it per feature and per user shows where money goes.

**Usage limit (quota).** A cap per user per day (for example 50 questions) that protects your budget from heavy users and abuse.

**Alert.** An automatic message (email, Slack) when something crosses a threshold: error rate above 2%, p95 above 5 seconds, daily cost above a limit.

**Unit test vs API (integration) test.** A **unit test** checks one function alone, like the chunker. An **API or integration test** calls a route and checks that the parts work together.

**Eval results table.** A short table in the README with your metrics on your golden set: for example retrieval hit rate, faithfulness, answer correctness, quiz JSON validity, average latency and cost per question.

**Limitations section.** An honest list of what the app does badly (scanned PDFs, very long books, non-English notes). It shows maturity, and interviewers often ask about it.

**Mistakes-log redo (DSA).** Re-solving problems you got wrong before, from a blank file, without looking at old code. It targets exactly your weak spots.

## End-of-week self-check

1. How do you make sure one user's notes never appear in another user's answers?
2. Why hash passwords, and why use a slow hash function?
3. What would you put in a health-check endpoint?
4. Your app costs more than expected. How do you find out why?
5. Name four fields every log line of an LLM request should have.
6. What does your CI pipeline check, and what would make it fail?
7. What are your capstone's three biggest limitations, and how would you fix each?
8. Why did you choose your vector database and cloud platform? (Give the trade-off.)

**Answers**

1. Store the `user_id` with every document, chunk and quiz; always filter retrieval and database queries by the logged-in user's ID taken from the verified token (never from the request body); and have an automated test that tries to read another user's data and expects failure.
2. If the database leaks, plain passwords are exposed immediately and reused on other sites. A salted, deliberately slow hash makes guessing each password very expensive for an attacker.
3. A quick check that the app is running and can reach its key dependencies (database, vector DB), returning 200 if healthy and an error code if not. Keep it fast and avoid calling the LLM in it.
4. Look at your per-request cost logs grouped by feature, user and model: find which route uses the most tokens, whether contexts are too long (too many or too large chunks), whether some users are very heavy, and whether caching is working.
5. Request ID, user ID (or a hashed ID), route or feature, model name, input tokens, output tokens, latency, cost and status or error. (Any four.)
6. It installs dependencies, runs linting, unit tests and API tests, and a small eval set. It fails if any test fails or if eval scores drop below set thresholds (for example faithfulness below 0.85).
7. Your own answer. Examples: scanned PDFs without text (add OCR), slow answers for big uploads (background ingestion with a queue), English-only quality (a multilingual embedding model and eval set).
8. Your own answer, with a trade-off. Example: "Chroma, because it is simple and free for a single-server app; for many users I would move to pgvector or Qdrant for better filtering and scaling. Cloud Run, because it gives HTTPS and scales to zero, so the demo costs almost nothing; the trade-off is cold starts."

## If you fall behind

The UI can stay basic. Alerts can be one simple email alert on errors. Do not skip auth with user-level filtering (Day 134), the deploy (Day 137) or cost logging (Day 138); they are what make the capstone stand out. If you are more than two days behind, cut quiz scoring from the UI and keep everything else.
