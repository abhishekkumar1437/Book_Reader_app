Case studies are how you get good at system design: you see the same building blocks combined in different ways, and you learn which trade-offs each product cares about. Do every case yourself first, on paper, before reading the chapter. From Day 131 you start your capstone project, which reuses everything you have built.

> **In simple words:** For each product, ask the same questions in the same order: what must it do, what data does it need, which model, how do the parts connect, how do we know it works, how does it scale, and what can go wrong. Then start building your biggest project.

## What each topic means

**Customer support agent.** An AI that answers customer questions (order status, refunds, policies) using a knowledge base and tools like "look up order". Key design points: grounding in policies, tool permissions, when to hand off to a human, and measuring resolution rate and customer satisfaction.

**Human handoff (escalation).** Passing the conversation to a human agent when the AI is unsure, the user is upset, or the action is risky (like a large refund). A good design passes a summary so the customer does not repeat everything.

**Resolution rate.** The share of conversations solved without a human. A main business metric for support bots, always read together with satisfaction, so the bot is not "resolving" by giving bad answers.

**Recommendation system.** Suggests items a user may like: products on Flipkart, videos on YouTube, songs on Spotify.

**Candidate generation (retrieval stage).** Quickly picking a few hundred possibly relevant items from millions, using cheap methods like embeddings, "people who bought X also bought Y", or popular items.

**Ranking stage.** Scoring those candidates with a stronger model using many features (user history, item details, time of day) and ordering them. Two stages keep the system both fast and accurate.

**Two-tower model.** A common retrieval model: one network embeds users, another embeds items, and a dot product scores the match. Item vectors can be pre-computed and searched with a vector index.

**Cold start.** Recommending for a new user or new item with no history. Fixes: popular or trending items, asking a few preferences at sign-up, and using item content (title, description, category embeddings).

**Implicit vs explicit feedback.** **Explicit**: ratings and likes. **Implicit**: clicks, watch time, purchases. Implicit data is far more plentiful but noisier.

**AI code assistant.** A tool that completes code, answers questions about a codebase, or makes changes. Key design points: gathering the right context (open files, related files, repository search), very low latency for inline completion, and evaluating with real tests.

**Fill-in-the-middle (FIM).** A way of prompting code models with the code before and after the cursor, so they can complete the gap in the middle, not only continue at the end.

**Repository context retrieval.** Finding the relevant code for a request using symbol indexes, embeddings of code chunks and the import graph, because a whole codebase does not fit in the prompt.

**Content moderation.** Detecting and acting on harmful content (hate, violence, spam, scams) in posts, comments, images or chats, at large scale.

**Moderation cascade.** Cheap fast filters (rules, hash matching of known bad content, small classifiers) handle most items; uncertain ones go to an LLM or a larger model; the hardest go to human reviewers. Each step is more expensive and more accurate.

**Policy.** The written rules of what is and is not allowed. Models are trained and evaluated against the policy, and it changes over time.

**Human review queue.** A list of items for trained people to judge. Their decisions also become new training data.

**Appeal.** A process for users to challenge a decision. Required for fairness, and a source of data about mistakes.

**Precision–recall trade-off in moderation.** Higher recall removes more harmful content but also more innocent posts (false positives); higher precision does the opposite. The threshold depends on the harm: stricter for child safety, looser for mild spam.

**Capstone project.** A larger final project that combines everything: RAG, LLM features, auth, a UI, deployment and monitoring. It shows you can build a complete product, not only a demo.

**MVP (Minimum Viable Product).** The smallest version that delivers the main value. Build the MVP end to end first, then add features. A deployed simple app beats an unfinished complex one.

**Requirements document.** A short page listing what the app must do, for whom, and the limits (cost, latency, privacy). It keeps the project focused.

**Quiz generation.** Using an LLM to write questions and answers from source text. To keep it reliable, ask for structured JSON, include the source chunk ID for each question, and check that the answer appears in the source.

**Hard DSA problems (second pass).** Problems that combine two patterns, like Word Search II (backtracking + trie) or Swim in Rising Water (Dijkstra or binary search + BFS). They teach you to recognise combinations.

## End-of-week self-check

1. In a support agent, when should the AI hand off to a human?
2. Why do recommendation systems use two stages?
3. How would you recommend items to a user who signed up 5 minutes ago?
4. Why can't an AI code assistant just put the whole repository in the prompt?
5. Describe a moderation cascade and why it saves money.
6. For moderation of scam messages on a payments app, would you favour precision or recall? Why?
7. What does "MVP first" mean for your capstone?
8. How do you make LLM-generated quiz questions trustworthy?

**Answers**

1. When the model's confidence is low or retrieval finds nothing relevant, when the user asks for a human or is clearly upset, when the action is risky or above a limit (large refunds, account changes), and when the same issue has failed twice.
2. Scoring millions of items with a rich model for every request is far too slow. A cheap first stage cuts millions down to hundreds; an accurate second stage ranks only those.
3. Show popular or trending items (maybe by location or the sign-up page they came from), ask for a few preferences, and use content-based similarity to any item they click; then quickly update as they interact.
4. Most repositories are far bigger than the context window, and even when they fit, it would be slow and expensive, and the model's attention would be spread over irrelevant code. Retrieval of the relevant files and symbols works better.
5. Cheap filters (rules, known-bad hashes, small classifiers) handle the large clear majority. Only uncertain items go to an LLM, and only the hardest go to humans. Since most content never reaches the expensive steps, total cost stays low while quality stays high.
6. Favour recall, with a review or warning step: missing a scam can cost users real money, while a false positive can be softened by showing a warning instead of blocking, and by allowing appeals.
7. Build the smallest version that works end to end (upload, ask, quiz, deployed) before adding extra features like more file types, better UI or analytics. Then improve step by step.
8. Ask for structured JSON with the source chunk for each question, check the answer actually appears in that source (with code or a second LLM check), use low temperature, and test a sample by hand.
