The first three days finish Phase 7 with the "operations" side: how models are served efficiently, how experiments and models are tracked, how AI code is tested and released, and how live systems are monitored. From Day 123 you start AI system design, the interview round where you design a whole AI product on a whiteboard in 45 minutes.

> **In simple words:** Serving is running the model fast and cheaply for many users. MLOps tools remember every experiment, test every change and watch the live system. System design is explaining, in a structured way, how all these parts fit together for a given product.

Estimation practice for Day 125 (example prices; always check current ones):

```text
Users: 100,000 (1 lakh), 5 questions/day each   -> 500,000 requests/day
Average: 2,000 input tokens (question + RAG context), 300 output tokens
Daily tokens: 1.0 billion input, 150 million output
Example price: $3 per million input, $15 per million output
Daily cost: 1,000 × $3 + 150 × $15 = $3,000 + $2,250 = $5,250 per day (~$157,500 per 30 days)
Average load: 500,000 / 86,400 s ≈ 5.8 requests/second; plan for a peak of ~5x ≈ 30 requests/second
```

Numbers like these are why caching, smaller models for easy questions, and shorter contexts matter so much.

## What each topic means

**Online vs batch inference.** **Online**: predict right away for each request (a chatbot). **Batch**: predict for many items at once on a schedule (score all customers every night). Batch is cheaper; online is needed when users are waiting.

**vLLM.** A popular open-source server for running LLMs on GPUs with very high throughput, thanks to PagedAttention (efficient KV-cache memory) and continuous batching.

**TGI (Text Generation Inference).** Hugging Face's LLM serving server, similar in purpose to vLLM.

**Ollama (serving).** Runs models locally with simple commands and an HTTP API; ideal for development and small private deployments, not for heavy traffic.

**Continuous batching.** Instead of waiting for a whole batch of requests to finish, the server adds new requests to the running batch as soon as others finish. GPUs stay busy and throughput rises a lot.

**Quantization for serving.** Running a model with 8-bit or 4-bit weights to fit on smaller or fewer GPUs and serve faster, with a small quality loss.

**GPU memory estimate.** Weights need about (parameters × bytes per parameter). 7B in 16-bit: 7 × 2 = 14 GB. 70B in 16-bit: 140 GB (needs several GPUs). 70B in 4-bit: about 35 GB. Add extra room for the KV cache and activations, often 20% or more depending on context length and batch size.

**Autoscaling.** Automatically adding servers when traffic rises and removing them when it falls. GPU servers start slowly, so scaling rules must react early.

**Throughput vs latency.** **Throughput**: how many requests or tokens per second the system handles. **Latency**: how long one request takes. Bigger batches raise throughput but can raise latency.

**Experiment tracking.** Recording every training run's code version, parameters, metrics and output files so you can compare and reproduce them.

**MLflow.** A popular open-source tool for experiment tracking, model packaging and a model registry.

**Model registry.** A central catalogue of trained models with versions and stages (for example "staging" and "production"), so everyone knows which model is live.

**DVC (Data Version Control).** A tool that versions large data files and models alongside Git, storing the files elsewhere and keeping small pointers in Git.

**CI/CD.** **Continuous Integration**: automatically test every change. **Continuous Delivery/Deployment**: automatically release changes that pass. Bugs are caught early and releases become routine.

**GitHub Actions.** GitHub's built-in CI/CD. A YAML file in `.github/workflows/` says what to run (install, lint, test) on each push or pull request.

**Unit tests for ML code.** Tests for data-cleaning functions, feature code, input validation and prompt-building, plus simple model checks (output shape, probabilities between 0 and 1).

**Eval in CI.** Running a small, fixed evaluation set on every change to prompts or models, and failing the build if quality drops below a threshold.

**Blue-green deployment.** Run the old (blue) and new (green) versions side by side and switch all traffic at once; switch back instantly if something breaks.

**Canary deployment.** Send a small share of traffic (say 5%) to the new version first, watch the metrics, then increase step by step.

**Shadow deployment.** The new model receives copies of real requests and its answers are logged but not shown to users. Safe way to compare models on live traffic.

**Logging and tracing.** **Logs** record events. A **trace** follows one request through every step (retrieval, each LLM call, each tool call) with timings, inputs and outputs. Essential for debugging RAG and agents.

**Langfuse, LangSmith, OpenTelemetry.** **Langfuse** (open source) and **LangSmith** (from LangChain) are LLM observability tools for traces, costs and evals. **OpenTelemetry** is an open standard for traces and metrics across any software.

**Data drift.** The input data changes over time (new products, new slang, a new user group), so the model sees inputs unlike its training data.

**Concept drift.** The relationship between inputs and the correct output changes. During a sale season "normal" buying behaviour changes, so a fraud model's old rules become wrong.

**p50, p95, p99 latency.** Percentiles of response time. p95 = 2 s means 95% of requests finish within 2 seconds. Averages hide slow requests; p95 and p99 show what the unluckiest users experience.

**Token cost tracking.** Logging input and output tokens per request, per user and per feature, and turning them into money, so you can spot expensive features and set budgets.

**Prompt caching.** A provider feature that stores the processed form of a long, repeated prompt prefix (like a big system prompt or document), making later calls with the same prefix cheaper and faster.

**Semantic caching.** Storing past questions and answers and reusing an answer when a new question is very similar in meaning. Saves cost, but needs a careful similarity threshold to avoid wrong answers.

**Fallback.** A backup plan when the main model fails or is slow: retry, switch to another model or provider, or return a helpful error.

**AI system design round.** An interview where you design an AI product end to end (for example "a support chatbot for a bank") and explain trade-offs. Unlike classic system design, it also covers data, model choice, evaluation and safety.

**Functional vs non-functional requirements.** **Functional**: what the system does ("answers questions from HR documents with citations"). **Non-functional**: how well ("p95 under 3 seconds, 10,000 users, data stays in India").

**LLM gateway / router.** A central service that all LLM calls go through. It handles keys, rate limits, logging, cost tracking, fallbacks, and can route easy requests to a cheaper model.

**Prompt store.** A place to keep versioned prompts outside the code, so they can be changed, tested and rolled back safely.

**Feature store.** A system that stores ML features (like "orders in the last 30 days") consistently for both training and real-time prediction.

**Queue.** A buffer of jobs between services. It absorbs traffic spikes and lets slow work (like document ingestion) run in the background.

**Latency budget.** Splitting the allowed response time between steps: for example 100 ms retrieval, 50 ms reranking, and the rest for the LLM.

**Model routing.** Sending each request to the cheapest model that can handle it, for example a small model for simple questions and a large model for hard ones.

**Back-of-envelope estimation.** Quick, rough math (users, requests per second, storage, cost) to size a system. Round numbers are fine; state your assumptions aloud.

## End-of-week self-check

1. How much GPU memory do the weights of a 13B model need in 16-bit? In 4-bit?
2. What is continuous batching and why does it raise throughput?
3. What is the difference between canary and shadow deployment?
4. Your RAG app's answers got worse last month, but the code did not change. What could have happened, and how would you find out?
5. Why do we report p95 latency and not only the average?
6. Explain prompt caching vs semantic caching.
7. What are the main steps of the AI system design framework?
8. 50,000 users each ask 4 questions a day. About how many requests per second is that on average?

**Answers**

1. 13 × 2 = 26 GB in 16-bit; about 13 × 0.5 = 6.5 GB in 4-bit, plus extra for the KV cache and activations.
2. The server adds new requests into the running batch as soon as any request finishes, instead of waiting for the whole batch. The GPU is never idle waiting for the longest request, so many more tokens per second are produced.
3. Canary sends a small share of real users to the new version and they see its answers. Shadow sends copies of requests to the new version, but users only see the old version's answers; the new answers are only logged.
4. Data drift (new kinds of questions or new documents), a change in the provider's model version, stale or broken ingestion, or an index that was not updated. Check traces and logs, run the golden eval set again, compare retrieval hit rate over time, and look at the questions with low scores.
5. The average hides slow requests. If 5% of users wait 15 seconds, the average can still look fine, but those users have a bad experience. p95 and p99 show the tail.
6. Prompt caching (a provider feature) reuses the processing of an identical prompt prefix, so it is always exact and safe. Semantic caching (your system) reuses a stored answer for a similar question, which saves the whole call but can return a wrong answer if the threshold is too loose.
7. Clarify requirements (functional and non-functional) → data (sources, size, freshness, privacy) → model choice → architecture (draw the components and data flow) → evaluation (offline and online) → scale, latency and cost → safety and failure modes, then wrap up with trade-offs and improvements.
8. 50,000 × 4 = 200,000 requests a day. 200,000 / 86,400 ≈ 2.3 requests per second on average; plan for a peak several times higher.
