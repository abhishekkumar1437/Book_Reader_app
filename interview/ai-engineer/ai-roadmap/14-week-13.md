This week teaches the most common AI Engineer task in industry: making an LLM answer correctly from your own documents. That technique is called RAG, and almost every company building with LLMs uses it. You start with good prompts, learn how text becomes searchable vectors, and on Day 89 start building your first main portfolio project.

> **In simple words:** A good prompt is a clear, specific instruction with examples. Embeddings turn text into vectors so you can find text by meaning. RAG = search your documents for the relevant parts, paste them into the prompt, and ask the LLM to answer only from them.

## What each topic means

**Prompt.** The full input you send to an LLM: system prompt, instructions, context and the question.

**Prompt engineering.** Writing prompts that make the model's output correct, consistent and in the right format. It is cheap, fast to change, and should always be tried before fine-tuning.

**Role / persona.** Telling the model who it is: "You are a careful tax assistant for Indian salaried employees." It sets tone and focus.

**Delimiters and XML tags.** Clear markers around different parts of the prompt, like `<document>...</document>` and `<question>...</question>`, so the model does not mix instructions with data.

**Zero-shot vs few-shot.** **Zero-shot**: only the instruction. **Few-shot**: the instruction plus a few input → output examples, which strongly guides format and style.

**Chain-of-thought (CoT).** Asking the model to reason step by step before answering. It improves multi-step problems. Reasoning models do this internally.

**Structured output.** Making the model return machine-readable data like JSON that matches a schema. Many APIs now have a structured-output or tool-based mode that guarantees valid JSON.

**Prompt template.** A prompt with placeholders filled by code: `f"Summarise this review in 1 line: {review}"`.

**Prompt chaining.** Splitting a big task into several LLM calls, where each output feeds the next (extract → check → write). Easier to debug than one giant prompt.

**Embedding (sentence embedding).** A vector of hundreds or thousands of numbers that represents the meaning of a whole sentence or paragraph. Texts with similar meaning have vectors that point in similar directions.

**Embedding model.** A model that produces embeddings, such as open sentence-transformers models or provider embedding APIs. It is different from the chat model; you must use the same embedding model for documents and queries.

**Semantic search.** Finding text by meaning: embed the query, then find the stored vectors with the highest cosine similarity. "How do I get my money back?" finds a passage about "refund policy" even with no shared words.

**Keyword search.** Finding text that contains the same words. Good for exact names, codes and IDs (like "IRCTC PNR 4521") where semantic search can fail.

**Vector database.** A database built to store embeddings and find the nearest ones fast, usually with extra fields (metadata) for filtering.

**ANN (Approximate Nearest Neighbour).** Search that finds almost the closest vectors much faster than checking every vector, accepting a small chance of missing the true best match.

**HNSW.** A popular ANN method: a multi-layer graph where you start with long jumps on sparse top layers and refine with short steps on dense lower layers. Fast and accurate, but uses more memory.

**IVF.** An ANN method that groups vectors into clusters and searches only the few clusters closest to the query.

**FAISS, Chroma, Pinecone, pgvector, Qdrant.** **FAISS**: a fast library, not a full database. **Chroma**: simple local vector DB, great for prototypes. **Pinecone**: fully managed cloud service. **pgvector**: vector search inside PostgreSQL, good if you already use Postgres. **Qdrant**: open-source vector DB with strong filtering, self-hosted or cloud.

**Metadata filtering.** Restricting search by fields like `{"department": "HR", "year": 2026}` so you only search the relevant documents. Also important for access control.

**RAG (Retrieval-Augmented Generation).** Retrieve relevant text from your data, add it to the prompt, then generate the answer. It gives the model fresh and private knowledge without retraining, and allows citations.

**Chunk and chunking.** Splitting documents into smaller pieces (for example 300–800 tokens) before embedding. Too small loses context; too big mixes topics and wastes prompt space.

**Chunk overlap.** Repeating a little text (say 10–20%) between neighbouring chunks so a sentence cut at a boundary still appears whole in one of them.

**Retriever and top-k.** The **retriever** is the part that finds chunks; **top-k** is how many it returns (often 3–10).

**Augment and generate.** **Augment**: put the retrieved chunks into the prompt with clear instructions ("Answer only from the context; say 'I don't know' if it is not there"). **Generate**: the LLM writes the answer.

**Citation.** Showing which document and page each part of the answer came from, so users can check it. It builds trust and helps catch hallucinations.

**Hybrid search.** Combining keyword search (BM25) and vector search, then merging the results (for example with reciprocal rank fusion). Usually better than either alone.

**BM25.** The standard keyword-ranking formula. It scores documents higher when they contain the query words often, especially rare words, with a correction for document length.

**Reranking and cross-encoder.** Retrieve, say, 30 candidates quickly, then re-score them with a slower, more accurate model. A **cross-encoder** reads the query and a chunk together and outputs a relevance score.

**Query rewriting.** Using an LLM to turn a vague or conversational question ("and what about for seniors?") into a clear search query.

**HyDE (Hypothetical Document Embeddings).** Ask the LLM to write a fake answer first, embed that, and search with it. A fake answer often looks more like the real passage than the short question does.

**Multi-query.** Generate several versions of the question, search with each, and combine the results to improve recall.

**Parent–child chunks.** Search over small chunks for precision, but send the larger parent section to the LLM for context.

**Contextual retrieval.** Adding a short description of where a chunk comes from ("This is from the 2026 leave policy, section on maternity leave") before embedding it, so chunks are easier to find.

**GraphRAG.** Building a knowledge graph of entities and relations from documents, then using it to answer questions that connect many documents.

**Agentic RAG.** An agent decides when to search, what to search for, and whether the results are good enough, possibly searching several times.

**Trie (DSA).** A tree of characters where each path from the root spells a prefix. Finds all words with a prefix fast, as in search-box autocomplete.

**Dynamic programming (DSA).** Solving a problem by combining answers to smaller overlapping sub-problems and storing them so each is computed once. Climbing Stairs: ways(n) = ways(n − 1) + ways(n − 2).

## End-of-week self-check

1. Name five things that make a prompt better.
2. When is few-shot prompting better than zero-shot?
3. Why must the same embedding model be used for documents and queries?
4. A user searches for an order ID "FK-88213". Why might pure vector search fail, and what fixes it?
5. List the seven steps of the RAG pipeline.
6. What goes wrong if chunks are too small? Too large?
7. What does a reranker do, and why not use it on all documents?
8. Why does RAG reduce hallucinations but not remove them?

**Answers**

1. A clear task, a role, the needed context, delimiters between instructions and data, examples of good output, a stated output format, and permission to say "I don't know". (Any five.)
2. When the output format or style is hard to describe in words, or the task is unusual. Two or three examples show the model exactly what you want.
3. Each embedding model has its own vector space. Vectors from two different models are not comparable, so similarity scores would be meaningless.
4. Embeddings capture meaning, not exact strings, so a rare code may land near unrelated texts. Hybrid search with BM25, or a metadata filter on the order ID field, fixes it.
5. Load documents, chunk them, embed the chunks, store them in a vector DB, retrieve the top-k chunks for a question, augment the prompt with them, generate the answer (with citations).
6. Too small: chunks lose context (a sentence without its heading or neighbours), so answers are incomplete. Too large: each chunk mixes several topics, similarity scores get blurry, and you waste context space and money.
7. It re-scores a shortlist of candidates with a more accurate (usually cross-encoder) model and reorders them. It is too slow to run on millions of documents, so you use fast retrieval first and rerank only the top 20–50.
8. The model now has relevant facts in the prompt, so it guesses less. But retrieval can miss the right chunk, chunks can be outdated or contradictory, and the model can still misread the context or add outside facts. You still need evaluation and citations.
